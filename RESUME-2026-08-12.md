`DriverEntry` never runs — the file log at `C:\Windows\Temp\iddseat.log` is
never created. So the framework rejects the driver before any of our code
executes, and `0xD000000D` (STATUS_INVALID_PARAMETER) has stayed **constant**
through every change: INF decoration, UMDF version 2.35→2.33, static CRT,
policy allow-list, driver version bumps.

That constancy is the point. Whatever rejects it decides before anything
version- or content-specific matters.

**The WUDF trace is the one thing that has never been read.** It is the
framework's own account of what it rejected. Everything else has been inferred
from outside.

## 4. Read it

The events are WPP-formatted, so `Get-WinEvent` may show them without message
text. Try it first — it is cheapest:

```powershell
Get-WinEvent -Path C:\ProgramData\Microsoft\WDF\WUDFTrace.etl -Oldest -MaxEvents 5000 -ErrorAction SilentlyContinue | Select-Object -Last 60 TimeCreated, Id, @{n='Msg';e={$_.Message -replace '\s+',' '}} | Format-Table -AutoSize -Wrap
```

If the messages are empty, decode with `tracefmt` from the WDK, which resolves
WPP with the framework's own TMF files:

```powershell
Get-ChildItem 'C:\Program Files (x86)\Windows Kits\10' -Recurse -Filter 'tracefmt.exe' -ErrorAction SilentlyContinue | Select-Object FullName
```

```powershell
cd C:\ProgramData\Microsoft\WDF; & '<tracefmt path>' WUDFTrace.etl -o wudf.txt -p C:\Symbols\TMF -r C:\Symbols
```

Failing that, `tracerpt` with no `-f` argument (the `-f XML` combination is
rejected — that error came up already):

```powershell
cd C:\ProgramData\Microsoft\WDF; tracerpt WUDFTrace.etl -o wudf.xml -summary wudf-summary.txt -y
```

**What to look for:** anything naming `iddseat`, `IddCx`, a version mismatch, a
missing interface, or a rejected config. The framework will say which parameter
it considered invalid.

## IF THE TRACE STILL SAYS NOTHING USEFUL

Two options, both heavier:

**A user-mode debugger on WUDFHost.** Set `HostProcessDbgBreakOnStart` under
`HKLM\SYSTEM\CurrentControlSet\Control\WUDF` (or via `WdfVerifier.exe`) and
attach. The docs are explicit that this needs a *user-mode* debugger, not a
kernel one, because a kernel debugger does not receive user-mode module load
notifications. This is the definitive answer but needs WinDbg and symbols.

**Build the WDK's own IddCx sample and install it.** If Microsoft's sample also
fails to load on this machine, the problem is environmental rather than in
`iddseat.cpp`, and that is worth knowing before spending more time on our code.
This is probably the cheaper of the two.

## STATE OF EVERYTHING

**Working and proven:**

- The RDS protocol provider creates and logs into a real Windows session with a
  full desktop — `explorer`, `dwm`, `winlogon`, teacher's own environment. No
  RDP anywhere in the path. Tagged `rdsprov-session`.
- The provider reaches `GetHardwareId`, hands over `HydraSeat_RemoteIDD_v1`, and
  the RD stack creates `SWD\RemoteDisplayEnum\...&SessionId_000N`.
- The driver package installs cleanly: `Device ... was configured. oem27.inf
  1.0.0.8, Status: 0`.
- Mode 3 / PROBLEM 2 is finished — `/gfx` crash root-caused
  (`update->DesktopResize` NULL), CPU spin fixed, glitching fixed by publishing
  on the gfx `EndFrame` callback. Confirmed clean by a student. Tagged
  `gfx-working`.

**Fixed along the way today** — four real defects, none visible before the
tracing existed:

1. Device installation policy `DenyUnspecified=1` was blocking the IDD outright.
   Now allow-listed by hardware ID under
   `HKLM\SOFTWARE\Policies\Microsoft\Windows\DeviceInstall\Restrictions\AllowDeviceIDs`.
2. `UmdfLibraryVersion = $UMDFVERSION$` was shipping as a literal token —
   `stampinf` needs `-u`.
3. `infverif` error 1199: `DIRID 13 (UMDF)` requires a `10.0...17134`
   decoration, not `16299`. Fixing this made `pnputil /add-driver /install`
   succeed on real devnodes for the first time.
4. The driver linked the **dynamic** CRT (`/MD`), pulling in `MSVCP140.dll`,
   `VCRUNTIME140*.dll` and the UCRT stubs, which WUDFHost cannot resolve.
   Now `/MT`; `dumpbin /dependents` shows system DLLs only and the binary went
   from 59KB to 220KB.

**The A/B that framed the whole thing:** with the driver package unstaged the
session survives and reaches `NotifyCommandProcessCreated`; with it staged the
connection dies with `PreDisconnect reason=17`. One variable, reproducible.

**Ruled out for the load failure:** `UmdfHostProcessSharing`, `GetInputHandles`
out-params, session arbitration, test-signing (active and verified), stale
devnodes (they are transient), UMDF 2.35 vs 2.33, and the static CRT — that last
one was a real bug but did not change the error.
