# INCIDENT — boot loop and Windows reset, 2026-08-12

**Outcome:** unrecoverable boot loop, resolved by `Reset this PC → Keep my files`.
**Root cause:** never established. Diagnostic logs were destroyed by the reset before
they were read.
**Cost:** one OS install, all applications, ~6 hours.

This is a hypothesis document, not a post-mortem. It records what was observed, what
was ruled out, and what remains possible. It does not claim a cause.

---

## 1. What changed before the failure

All within roughly one hour of the reboot that failed, all from the driver work
tracked in `ATTACK-PLAN.md`:

| # | Change | Scope |
|---|--------|-------|
| 1 | Staged remote IDD package `iddseat-remote.inf` as `oem27.inf` | driver store |
| 2 | Device installation policy allow-list (`DenyUnspecified=1` bypass by hardware ID) | machine-wide policy |
| 3 | Registered RDS protocol provider — `HydraProto` listener key + COM registration | `termsrv` load path |
| 4 | WUDF diagnostic logging registry values (`LogEnable`) | `HKLM\SOFTWARE\...\WUDF` |
| 5 | Reboot | — |

Prior state also included, from earlier sessions: the console IDD package
(`dist\driver\iddseat.inf`), `hydrakbd` (KMDF keyboard filter), Interception
(class UpperFilters on keyboard and mouse), RDP-Wrapper, and the Hydra service.

**Note:** the session's own cleanup command included `rdsprov-register.ps1 -Unregister
-Apply`. Whether it completed before the reboot was never confirmed.

## 2. Failure signature

- Startup Repair screen: *"Your device ran into a problem and couldn't be repaired"*
- Later, after BCD edits: **true reboot loop** — black screen, then reboot
- **Never** black-and-hung. It always rebooted. Rules out "booting fine, failing to display."
- **No minidump.** `D:\Windows\Minidump` empty. **Not a bugcheck.** No driver crashed
  in the ordinary sense, or it failed before the dump stack was available.
- **No restore points.** System Protection was off by policy (deliberate — see §6).
- BitLocker off. Disk fully readable from WinRE throughout.

## 3. SrtTrail was worthless

```
Root cause found:
Start network for cloud remediation
Error code = 0x4C6
```

`0x4C6` is `ERROR_NO_NETWORK`. This is Startup Repair failing to reach Microsoft's
cloud remediation service — WinRE had no NIC driver or no DHCP. It is a diagnostic
failure, not a finding. Startup Repair never diagnosed the actual fault.

**Lesson:** a `Root cause found` block naming a network error means the tool gave up.
Do not treat it as evidence.

## 4. What was ruled out

Each of these was undone offline and **changed nothing**:

| Suspect | Action taken | Result |
|---|---|---|
| Remote IDD package | `dism /image:D:\ /remove-driver /driver:oem27.inf` | removed, verified gone, still looped |
| Safe Mode flag | `bcdedit ... /deletevalue {default} safeboot` | still looped |
| Interception keyboard filter | `UpperFilters` = `keyboard\0kbdclass` → `kbdclass` | still looped |
| Interception mouse filter | `UpperFilters` = `mouse\0mouclass` → `mouclass` | still looped |

Four undos, no change. Strong evidence that none of these was the cause — if a
failed device install had broken the boot, removing the package should have fixed it.

**Loose ends never closed:** the console IDD package and `hydrakbd` were never
confirmed removed. Neither appeared in `UpperFilters`, so `hydrakbd` was likely
staged but unbound.

## 5. Remaining hypotheses, ranked

### H1 — Servicing stack transaction (strongest)

`dism /image:D:\ /cleanup-image /revertpendingactions` returned **`0x800f082f`**.
This was the single anomalous return of the entire night and was never explained.

A half-committed CBS transaction produces exactly this signature: reboot loop, no
bugcheck, no minidump, Startup Repair defeated, and every driver-level undo
irrelevant because the fault is above the driver layer. `pending.xml` was flagged
for renaming but its existence was never confirmed.

**Fits all observed evidence. Untestable now — CBS.log is gone.**

### H2 — RDS protocol provider

The `HydraProto` listener key causes `termsrv` to load a custom provider DLL at
boot. If `-Unregister` did not complete, that DLL was loading into a service that
starts automatically. Weakened by the fact that `TermService` failing does not
normally prevent a boot.

### H3 — Device installation policy edit

The `DenyUnspecified` allow-listing was the only change that touched machine-wide
policy rather than a single package. Broader blast radius than anything else on the
list, and it was not undone offline.

### H4 — Hardware

Surface Book 3 SSDs fail in this shape. Argued against by the reset completing
cleanly and the machine being stable since. Keep on the list; if instability
recurs without driver work, it climbs to the top.

## 6. What made recovery worse

Recorded plainly, because these are the reusable lessons.

### 6.1 WinRE `HKLM` is not the installed system's registry

The first hour of recovery was spent running `reg add`, `reg delete`, and `pnputil`
from the WinRE command prompt. **All were no-ops.** WinRE boots its own OS from
`winre.wim` with its own hives in RAM. `HKLM\SYSTEM` there is WinPE's, not the
installed system's.

This is why `reg delete ...\WinStations\HydraProto` reported the key did not exist —
correctly, because WinPE never had one.

**Correct offline forms:**

```
reg load HKLM\OFFSYS D:\Windows\System32\config\SYSTEM
reg query "HKLM\OFFSYS\ControlSet001\..."
reg unload HKLM\OFFSYS
```

```
dism /image:D:\ /remove-driver /driver:oemNN.inf
```

Also: `CurrentControlSet` does not resolve offline — use `ControlSet001`, and check
`HKLM\OFFSYS\Select\Current` (`0x1` = 001, `0x2` = 002) before trusting any edit.

Also: **drive letters are reassigned on every WinRE boot.** Re-detect each time:

```
for %d in (C D E F G) do @if exist %d:\Windows\System32\ntoskrnl.exe echo %d:
```

### 6.2 `bootstatuspolicy ignoreallfailures` locked out recovery

Set alongside `safeboot minimal` with the intent of seeing the real failure instead
of the Startup Repair screen. It suppresses automatic failover into WinRE — which
was the only remaining route into the machine. **This turned a recoverable state
into one requiring external boot media.**

**Never set this on a machine that is already failing to boot.** It is a debugging
aid for a machine that boots, not a recovery tool.

### 6.3 No recovery media existed

A recovery stick had been made for the June ASTER work and was never rebuilt. Its
absence cost several hours and forced a full reset that a working stick would have
avoided. This was the single most expensive omission.

### 6.4 Logs were destroyed before being read

`Reset this PC` clears Windows' own log directories. After the reset, all three were
gone from `C:\Windows.old`:

- `Windows\INF\setupapi.dev.log` — full device install trace
- `Windows\Logs\CBS\CBS.log` — would have explained `0x800f082f`
- `Windows\System32\winevt\Logs\System.evtx` — boot sequence to the failure

**Copy these to removable media before any reset. They are the only evidence that
matters and they are small.**

## 7. Standing rules going forward

1. **No driver package install without a tested recovery stick physically present.**
   Precondition for every `pnputil`, `dism /add-driver`, and installer that ships a
   `.sys`. Not "made once" — verified bootable.
2. **Never set `bootstatuspolicy ignoreallfailures`** on a machine in a failed state.
3. **Capture logs before any destructive recovery step.** The three files in §6.4.
4. **Driver inventory after every install, stored off-machine** (committed to this
   repo, not left on the disk that may not boot):
   ```powershell
   dism /online /get-drivers /format:table > .\driver-inventory-$(Get-Date -f yyyyMMdd-HHmm).txt
   ```
5. **Known-good class filter values, recorded 2026-08-12 on the clean system:**
   ```
   {4D36E96B-E325-11CE-BFC1-08002BE10318}  UpperFilters = kbdclass
   {4D36E96F-E325-11CE-BFC1-08002BE10318}  UpperFilters = mouclass
   ```
   These two values are the entire recovery if Interception breaks input again.
6. **Test signing** for driver iteration, so packages install without touching CI
   policy and unwind cleanly.
7. **System Protection stays off** — deliberate. Restore points sit in
   `System Volume Information` where scanners cannot reach, and a restore can
   reinstate a cleaned payload. The recovery stick is the net instead.
8. **Mode 3 needs no drivers.** `hydrardp` + `mirror` are user-mode binaries from
   this repo. Nothing in the mode 3 path can prevent a boot. Driver work is a
   separate, gated activity.
9. **Separate the teaching machine from the development machine.** Every failure
   here came from the two being the same box. A second-hand ThinkPad ends this
   category of evening permanently.

## 8. Recovery procedure (validated 2026-08-12)

For the next time, since this sequence actually worked:

1. Build media on another PC: `recoverydrive.exe`, **untick "Back up system files"**
   (~700 MB instead of 5.5 GB). Full format, FAT32.
2. Surface Book 3: nothing else plugged in, stick in a **base USB-A** port. Shut down.
   Hold **Volume Down**, press and release **Power**, keep holding until spinning
   dots appear. (**Volume Up** + Power is UEFI settings — different combination.)
3. Troubleshoot → Advanced options → Command Prompt.
4. Re-detect drive letters (§6.1). Copy off the three log files (§6.4).
5. Undo BCD damage:
   ```
   mountvol S: /s
   bcdedit /store S:\EFI\Microsoft\Boot\BCD /deletevalue {default} safeboot
   bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} bootstatuspolicy displayallfailures
   ```
6. Offline driver removal and hive edits as needed (§6.1).
7. Reset only if the above fails: **Keep my files** → **Local reinstall** (not Cloud;
   network was unavailable throughout this incident).

## 9. Post-reset state

**Survived:** `C:\Scripts`, `C:\Programs\hydra` (working tree clean, tracking
`origin/main`, all tags present including `gfx-working` and `rdsprov-session`),
PowerShell 7 (per-user install), the PowerShell profile via OneDrive.

**Lost:** all applications — VS Build Tools, git, MSYS2, Python, Notepad++,
RDP-Wrapper, Interception, ASTER. All Windows logs.

**Rebuilt same day:** VS Build Tools (`cl 19.44.35228` — matches the canonical
toolchain), git, MSYS2 base, Hydra Shell shortcut. The shortcut failure was
incidental: it hardcodes an absolute path to `vcvars64.bat` discovered at creation
time, and the reset removed it.

## 10. Unrelated findings from the same session

Recorded here because they surfaced during recovery and are easy to lose.

- **`dist\driver\iddseat.inf` still ships the literal `$UMDFVERSION$` token.** The
  remote package `dist\driver-remote\iddseat-remote.inf` was hand-fixed to `2.33.0`
  in `fb346cb`; the console package never was. Installing it standalone would fail
  with error 87 for a bug already fixed elsewhere.
- **`build-driver.ps1` never runs `stampinf`** — line 122 only prints a reminder.
  `build-kbfilter.ps1` does run it (lines 95–97), which is why the KMDF package is
  correct and the UMDF one is not.
- **Porting that stampinf call would not fix the token.** It uses `-f -d -a -v`,
  which set `DriverVer`, not `UmdfLibraryVersion`. `hydrakbd` is KMDF and has no
  `UmdfLibraryVersion` line at all. The fix is an explicit substitution step in
  `build-driver.ps1` — read source INF, replace token, write to `dist`.
- **Error 87 was already solved** (`1a36bdf`, `fb346cb`). The live driver blocker is
  **`0xD000000D` before `DriverEntry` runs**, constant across UMDF 2.35 → 2.33.
  `ATTACK-PLAN.md` Lead 1 is closed.
