## WHAT WAS SOLVED TODAY

**PROBLEM 2 — the /gfx crash. Root cause found and fixed.**

`update->DesktopResize` was NULL. `gdi_graphics_pipeline_init` sends
ResetGraphics on attach, the server answers with a desktop-size notification,
and libfreerdp calls `update->DesktopResize(gdi->context)` having checked only
that `update` itself is non-NULL:

```
libfreerdp3.dll+0xDCB4B:
    test %r14,%r14          <- checks the struct
    je   ...
    mov  (%r12),%rcx        <- r12 = gdi, *gdi = gdi->context
    call *0x68(%r14)        <- does NOT check the slot
```

`offsetof(rdpUpdate, DesktopResize) == 0x068`, confirmed by compiling
`rdp/offs.c`. Without `/gfx` that path never runs, which is why every non-gfx
run was clean and eleven hypotheses missed it — none looked at `rdpUpdate`.

Found by `rdp/hydra_veh.c`, a first-chance vectored exception handler that
dumps `[rsp+00]` resolved to module+RVA. The `call` pushes its return address
before faulting, so that value names the caller. One run, no guessing.

**Patches applied and working** (each with `-Revert`, backups as
`rdp/hydrardp.c.bak-*`):

| Script | Effect |
|---|---|
| `fix-desktopresize.ps1` | added `hydra_desktop_resize()`, the actual fix |
| `fix-pointerbisect.ps1` | removed the gfx guard on pointer registration |
| `fix-endpaint.ps1` | installs `hydra_end_paint` after gfx attach, always chains |
| `fix-throttle-early2.ps1` | throttle check moved to function entry; CPU ~200% → normal |

**Reverted, did not work:** `fix-gfx-signal.ps1` — publishing from
`hydra_gfx_update_surface_area` froze the panel on frame 1. That callback never
fires on this server; it uses frame markers instead.

## THE ONE OPEN ITEM: video is still glitchy

Ruled out, with measurements:

- **not the codec** — `/gfx:RFX` attaches and decodes
- **not CPU** — was ~200% from a spinning loop, now ~93s total, picture unchanged
- **not the throttle** — 60fps publishing, `coalesced` counts skipped calls not
  lost frames (an earlier reading of "96% of frames discarded" was wrong)
- **not surface-area timing** — that callback does not fire at all here

**Next thing to try: `EndFrame` on the `RdpgfxClientContext`.** That is the PDU
this server actually sends to mark a completed frame. `gdi_graphics_pipeline_init_ex`
fills that slot; capture it and chain, exactly as `fix-endpaint.ps1` does for
`update->EndPaint`. The slot is `pcRdpgfxEndFrame EndFrame` at offset 0x20 in
`s_rdpgfx_client_context` (`C:\msys64\mingw64\include\freerdp3\freerdp\client\rdpgfx.h`).

The theory being tested: the main loop samples `gdi->primary_buffer` on a blind
16ms timer with no relationship to when gfx finishes a blit, so it can copy
mid-blit and publish a frame that is part new and part old.

## Traps hit repeatedly. Read before patching.

- `hydrardp <seat> <user> [password] [host]` — `argv[3]` is the **password**.
  The gfx switch is the **`HYDRA_GFX` env var**, never a command-line flag.
- **A running `hydrardp` locks `dist\hydrardp.exe`.** The compile succeeds, the
  link fails with `Permission denied`, and a **stale binary** is left behind.
  Always `Stop-Process -Name hydrardp -Force` first, and always check
  `LastWriteTime` after.
- `hydrardp.c` has **mixed line endings** (1048 CRLF, 44 bare LF from the patch
  scripts). Literal-string anchors fail. Build patterns with `\r?\n`.
- Logs under `C:\ProgramData\Hydra\logs` are **startup-only**. `hydra-shm.ps1`
  reads live state from shared memory instead — run it elevated.
- `hydractl status` needs elevation or returns `err 5`.
