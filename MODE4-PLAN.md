# MODE4-PLAN.md — remote-session IDD, built on a driver that loads

Written 2026-08-17, immediately after mode 6 came up. Everything here follows
from one fact established today: **VDD and Microsoft's sample both load on this
machine; `iddseat.dll` does not.** So the way to mode 4 is a source tree that
already works, not a rewrite of ours.

---

## 0. Why mode 4 is still worth doing, and mode 5 is not

**Mode 5 is now redundant.** Its goal was a console-side IddCx driver. VDD is
exactly that, working. The only thing `iddseat.cpp` would add is per-seat EDID
and mode control, and `vdd_settings.xml` already covers resolutions. Fixing
`0xD000000D` is a curiosity now, not a capability. Park it.

**Mode 4 is different.** Its value was never "a virtual display" — it is *seat
B's session having its own display*. That removes the RDP round trip, the
client, the DDA capture, the shared ring and `mirror` from the pixel path
entirely. Everything modes 1–3 fight with — Suppress Output, client visibility,
capture stalls, cursor compositing, the 800ms agent timing — exists only because
the seat's pixels have to travel.

PnP display devices are machine-global. The only way a *session* gets one is a
remote-session IDD that the RD stack instantiates. That is what `HydraProto`
exists for, and it is why mode 6 does not substitute for mode 4.

---

## 1. What today established that changes the odds

**The driver source is the fault, and we have a working one.** Three IddCx
drivers tested on this machine:

| driver | devgen devnode | app devnode | hydrad devnode |
|---|---|---|---|
| Microsoft IddSampleDriver | **loads** | **loads** | fails 0xD000000D |
| MttVDD (VDD 25.7.23) | **loads** | — | — |
| our iddseat | fails | — | fails |

Ours fails on *every* devnode type. So the INF, packaging, catalog, signing,
class-extension binding and devnode shape are all proven good by direct
comparison — the defect is inside `iddseat.dll`.

**The provider does not need RDP-Wrapper.** With `ServiceDll` at stock
`termsrv.dll`, `query session` showed the console session and `hydraproto#0`
concurrently. `NEXT-STEPS.md` had this as an open question and called its own
answer inference. It is fact.

**A provider session with no IDD stalls at logon.** With every IDD unstaged, the
provider session authenticates cleanly (Security 4624, Logon Type 10
RemoteInteractive, no 4625) and then sits at `LogonUI` forever — Winlogon 7001
never fires, at 8s, 16s and 24s, warm profile and cold. So winlogon appears to
need a display target to complete the desktop switch.

**Those two fit together.** A working remote IDD should let logon complete *and*
supply the display. The stall is not a separate problem to solve first.

**Registry names the class extension.**
`HKLM\SYSTEM\CurrentControlSet\Control\Wdf\UMDF\IddCx\Versions\1\2` has
`Service = IddCx0102`. That is the only registered version, regardless of which
IddCx headers the kit ships. `UmdfExtensions = IddCx0102`, always.

## 2. The plan

### Step 1 — get VDD's source building with our recipe

```powershell
mkdir C:\Programs\vddsrc -Force; cd C:\Programs\vddsrc
Invoke-WebRequest 'https://github.com/VirtualDrivers/Virtual-Display-Driver/archive/refs/tags/25.7.23.zip' -OutFile src.zip
Expand-Archive src.zip -DestinationPath . -Force
Get-ChildItem -Recurse -Include *.cpp,*.h,*.inf -Name
```

Build it with `build-mssample.ps1`'s recipe rather than its own vcxproj — that
recipe is proven to produce loadable IddCx drivers from third-party source, and
the vcxproj route dies on `wudfwdm.h` because it carries no WDK include paths.

Expect the same two obstacles the sample had:

- **`STATUS_WAIT_0` undeclared** in `corewrappers.h` — caused by
  `/DWIN32_NO_STATUS`. Drop that define and add
  `Include\<sdk>\winrt` to the include list.
- **`Driver.tmh` missing** — WPP tracing, generated by `tracewpp` which we do
  not run. Force-include a stub that no-ops `WPP_INIT_TRACING`, `WPP_CLEANUP`
  and `TraceEvents`, and create an empty `.tmh`.

**GATE: build it unmodified first and confirm it loads via `devgen`.** If a
build from source does not load when the shipped binary does, stop — something
in the recipe differs and no amount of remote-session work will help.

### Step 2 — make it a remote-session driver

Two changes, both in `IddCxAdapterInitAsync`'s caps, mirroring what
`iddseat.cpp` does under `/DHYDRA_REMOTE_IDD`:

```c
AdapterCaps.Flags = IDDCX_ADAPTER_FLAGS_REMOTE_SESSION_DRIVER
                  | IDDCX_ADAPTER_FLAGS_USE_SMALLEST_MODE;
```

`USE_SMALLEST_MODE` is mandatory alongside the remote flag.

And `IddCxAdapterDisplayConfigUpdate2` after adapter init — without it a remote
session's display paths never activate (`3465b75`). That call needs **IddCx
1.10 minimum**, which is a problem: the only registered extension is 1.2.
Resolve this before building. If 1.10 genuinely cannot bind on this OS, the
remote path may be closed on 24H2 and that is worth knowing early.

**The hard gate to remember:** the OS fails `IddCxAdapterInitAsync` if the
remote flag is set on a device the RD stack did not create, *and* if it is absent
on one the stack did. There is no way to test a remote IDD with `devgen`. It has
to come up through `HydraProto`.

### Step 3 — remote INF shape

From `iddseat-remote.inf`, which documents this correctly even though its driver
does not work:

- Bare hardware ID, **no `Root\` prefix** — the RD stack creates the devnode
- `UmdfHostProcessSharing = ProcessSharingDisabled` — one host per session
- **No `DeviceGroupId`** — grouping defeats per-session isolation
- `UmdfExtensions = IddCx0102`
- `ServiceBinary = %12%\UMDF\<name>.dll`, `DestinationDirs UMDriverCopy = 12,UMDF`
- `AddReg` in `.NT.hw` with `HKR,, "UpperFilters", 0x00010000, "IndirectKmd"`
- Its own CatalogFile and service name, so console and remote packages can
  coexist in the store

### Step 4 — provider

```powershell
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\TermService\Parameters' -Name ServiceDll -Value 'C:\WINDOWS\System32\termsrv.dll' -Type ExpandString
Restart-Service TermService -Force; Start-Sleep 10
.\rdsprov-register.ps1 -Register -Apply
```

**`-Register` recreates the listener key EMPTY every time.** Credentials must be
re-set after every register — `Username=teacher`, `Domain=''` (empty, not the
machine name). This has been forgotten six times.

Trigger with `C:\TestProtocol\createconnection.txt`.

Watch `provider.log`. The 08-12 sequence to compare against:

```
EnableWddmIdd(1)          <-- termsrv TELLING us the mode, not asking
AcceptConnection
GetClientData
AuthenticateClientToSession
NotifySessionId
GetInputHandles
GetHardwareId             *** the stack asking for the driver *** count=200
ConnectNotify session=N   (IDD creation starts here)
NotifyCommandProcessCreated session=N
PreDisconnect reason=17   <-- with a broken driver staged, at ~1.2s
```

`reason=17` at ~1s means the driver failed. `reason=12` at ~33s means it timed
out waiting. Neither, and the session persisting, is the win.

### Step 5 — verify

```powershell
query session
Get-CimInstance Win32_Process -Filter "SessionId=<n>" | Select-Object Name | Sort-Object Name
```

`explorer.exe`, `dwm.exe`, and **no `LogonUI.exe`** means logon completed —
which it never has without a display.

Then point `session_capture` at that session and read the ring. If `seq`
advances, mode 4 is real and the RDP path becomes optional.

## 3. Traps, all paid for already

- Stale `SessionId` devnodes in `CM_PROB_FAILED_ADD` block retriggering. Reboot
  between attempts.
- A registered provider **locks its own DLL**: unregister → build → register.
- Never leave the listener registered with the trigger file present — the next
  boot fires a connection on its own.
- `hydrad`'s `SwDeviceCreate` produces devnodes that IddCx drivers will not load
  on, for reasons still unknown. Three drivers, same result. Irrelevant for
  mode 4 (the RD stack creates the devnode) but it is why mode 6 uses `devgen`.
- **Emergency undo**, physical console only:

```
reg delete "HKLM\System\CurrentControlSet\Control\Terminal Server\WinStations\HydraProto" /f
sc stop TermService
sc start TermService
```

- **Restore `rdpwrap.dll` afterwards** or modes 1–3 silently lose their second
  session:

```powershell
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\TermService\Parameters' -Name ServiceDll -Value 'C:\Program Files\RDP Wrapper\rdpwrap.dll' -Type ExpandString
Restart-Service TermService -Force
```

- `safety-gate.ps1` before any `pnputil /add-driver`.

## 4. Honest assessment

The riskiest step is the IddCx version. `IddCxAdapterDisplayConfigUpdate2` needs
1.10; the only registered class extension is 1.2. If a driver declaring
`IddCx0102` cannot make that call, remote-session IDDs may not be reachable on
this build of 24H2 at all — and that is worth establishing in the first hour
rather than the third day.

Everything else is now assembly rather than discovery: a driver source that
loads, a build recipe that works, an INF shape documented from experience, a
provider that creates sessions, and a known-good undo path.

If step 2 turns out to be blocked, mode 6 is a genuinely good outcome and modes
1–3 are unaffected.

## 5. Mode 6 scaling — a third seat, no driver work

Deferred, but it is a two-line change when wanted.

`vdd_settings.xml` has:

```xml
<monitors>
    <count>1</count>
</monitors>
```

Set `<count>2</count>` and VDD presents two virtual displays. Each gets its own
parked fullscreen client, its own seat session, its own `mirror` on a physical
panel. Seat C costs a `seats.toml` entry and a physical monitor — no driver work
at all.

Practical notes for when that day comes:

- Place every virtual display far from the real ones and from each other.
  Current: VDD at `(0,-1080)`, directly above the console panel.
- `DISPLAY<n>` numbers **shift** as devices come and go — it was DISPLAY4, then
  DISPLAY5 within one session. Always read the index from
  `sdl-freerdp /list:monitor` or `clip_console.exe` at launch, never hardcode.
- `clip_console.exe` reports true pixels; `[System.Windows.Forms.Screen]` does
  not (it reported the 3240x2160 console panel as 926x617).
- The virtual displays are on the **console** session. They are where the
  clients live, not where the seats live.
- Each extra seat is another `sdl-freerdp` and another `mirror`, so watch CPU
  before promising a third seat to anyone.

Recreate the VDD device after a driver reinstall:

```powershell
& 'C:\Program Files (x86)\Windows Kits\10\Tools\10.0.26100.0\x64\devgen.exe' /add /hardwareid "Root\MttVDD"
```

It persists across reboots. Remove with `devgen /remove`.
